# Tool reference

This is the detailed reference for every tool: arguments, checks, results and the evidence behind each operation. For a short index, see [Tools](tools.md). For setup, see [Setup](setup.md). For what has and has not been observed in ShowKontrol, see [Evidence and limits](evidence.md).

The MCP tool schemas returned by `tools/list` define the accepted arguments. This page explains behavior and limits; when the two differ, the schema is correct and this page needs a fix.

Common rules for offline tools:

- Inspect the source first. Tools that edit an existing file take its inspected SHA-256 and fail if the file changed.
- Write tools create a new destination and do not replace an existing file. Many publish with a hard link, so the destination filesystem must support hard links.
- A failed call publishes nothing, and the source is not modified.
- Indices are zero-based unless stated otherwise.

## Live API

These tools call the running ShowKontrol web engine. Write tools can change the show and control equipment.

### Read and observe

- `showkontrol_read`: call a JSON or text GET endpoint under `/api/v1`.

- `showkontrol_read_binary`: read a binary endpoint as an embedded base64 resource, limited to 5 MiB.

- `showkontrol_sample_events`: sample the event stream for up to 30 seconds and 100 events. The server can replay the most recent event of each type when the connection starts.

- `showkontrol_discover`: read live state, status, nodes, available node types, settings, variables, or the patch.

- `showkontrol_get_plays`: read `/data/plays` with a limit from 1 to 100 (default 20). `showkontrol_get_insights` reads `/data/insights`. Both return the API response without interpreting it. An empty response does not prove that no play history exists. Both tools returned responses through MCP from R27 27.0.11 in a live test. These responses can contain sensitive play data; do not put them or credentials in shared logs. Keep credentials in the private environment described in [Setup](setup.md#environment-variables).

- `showkontrol_get_deck`: read deck detail. Its frame playback data may be stale. Use `showkontrol_get_live_deck` to observe live transport state from `/state`; it returns the exact deck and any `t`, `tick`, and `epochMs` values supplied in the same response.

- `showkontrol_diagnose_live_node`: read one node by ID and compare the `node.stopped` parameter with the top-level `stopped` value. The result includes the node ID, title, type, raw values, and a warning when the boolean values differ. Missing, malformed, or duplicate parameter values are `unknown`. A difference does not establish its cause. On R27, the effective getter can reflect license or seal conditions. A live MCP test detected the mismatch on a temporary group node. At nearly the same time, the group type reported licensed and E-STOP was off. These checks do not establish the cause. The test removed the node and restored the baseline node IDs.

### Actions, transport and generic writes

- `showkontrol_write`: call a POST, PUT, PATCH or DELETE endpoint with a JSON body. Discover the endpoint and its schema first. This tool can change the show and control equipment.

- `showkontrol_deck_command`: send a documented transport command.

- `showkontrol_list_actions`, `showkontrol_get_action`: list action metadata or read metadata for one action ID. A live R27 27.0.11 test listed actions and read `app.player.load` through MCP. Metadata parameter names do not necessarily match POST JSON fields. Do not infer the request body schema from this metadata. In a disposable R27 27.0.11 session, `app.player.load` accepted `{"appact.deck":"1","appact.track":"__MCP_NONEXISTENT_TRACK__"}` with HTTP 200. No track load was observed. A second request for the test track also returned HTTP 200, while the player remained empty; that track had no verified audio clip. An HTTP success therefore does not establish that the action had its intended effect. Inspect the relevant player, node, or event state after an action.

- `showkontrol_search_actions`: filter the live action catalogue by exact category and text in the ID or label. Results are paginated. An offset can change if the catalogue changes. Read individual action metadata before use; it does not establish the request body schema.

- `showkontrol_run_action`, `showkontrol_session_command`: run an action, launch the show, or switch a screen. The manual does not specify all request bodies; supply the body expected by the running app. In R27 27.0.11, static inspection shows that session launch opens the Live screen for the current session and does not use request body fields. It does not open another session. These calls can control equipment.

  In a disposable R27 27.0.11 session, `app.screen.cueeditor` with an empty body returned success and the Cue Editor became visible with the selected test track. This test did not verify importing or editing a timeline.

  In a disposable R27 27.0.11 session, `showkontrol_run_action` with `app.node.bypass_on` and `{"appact.node":"<node title>"}` changed a disconnected temporary group's `node.bypassed` value from `false` to `true`. `app.node.bypass_off` changed it back to `false`. Both values were read through `showkontrol_get_parameter`. The test deleted the group and verified the original node IDs and connections. This checks those actions on one group, not their effect on connected equipment.

### Nodes and parameters

- `showkontrol_set_node_bypass`: set `node.bypassed` using a node ID and a boolean. The tool checks that the ID and its nonempty exact title are unique in `/nodes`, sends one bypass action, and reads the parameter by ID. A timeout or failed write has an unknown outcome. A failed or malformed readback is unknown; a different value is a mismatch. No write is retried. The action addresses a title, so a concurrent rename or the app’s title matching rules can select another node. These checks are not atomic, and a matching readback does not prove which node the action affected. The tool was tested on a disconnected group in R27 27.0.11; it reported matching readbacks for bypass on and off.

- `showkontrol_set_parameter_verified`: send one live parameter PUT by node ID and key, then read the same parameter. The value can be any JSON value. The result is `matched`, `mismatch`, `readback_unknown`, or `write_unknown`. A failed or malformed write response has an unknown outcome; the tool does not retry. The tool requires both PUT and GET responses to be objects with the exact `key` and a `value`. A live R27 test returned this shape for a text parameter, with additional label, category, and kind fields; other parameter types are not verified. The tool accepts only IDs in the observed `n` followed by digits format. It does not check node existence or protect against concurrent deletion or ID reuse. The comparison is deep and type-sensitive. Failure results do not include parameter values. The two requests are not atomic: another writer can change the parameter during or after the operation. A matching value may already have existed and does not prove that this write caused it. Inspect live state before deciding on a further write.

- `showkontrol_get_parameter`, `showkontrol_set_parameter`, `showkontrol_set_setting`, `showkontrol_fire_node`: common node and setting operations.

- `showkontrol_node_type_detail`, `showkontrol_create_node`, `showkontrol_delete_node`: inspect a node type and preview, create, or delete a node. Creation requires an explicit `dryRun` value. Optional `params` supplies a JSON object of node settings. In a live R27 27.0.11 dry-run test, supplied settings produced a configured preview with its final title. Creation with these settings and other node types remain unverified.

- `showkontrol_validate_node_settings`: check typed proposed values against the running app’s node-type metadata. Dynamic constraints, XML serialization, and actual app acceptance are not validated.

### Connections and the running patch

- `showkontrol_list_connections`, `showkontrol_create_connection`, `showkontrol_delete_connection`: list and edit connections by node ID and pin name or index. Creation requires an explicit `dryRun` value.

- `showkontrol_verify_live_connections`: read connections once and compare up to 100 expected wires by node ID and optional pin index or exact pin label. Omitted pins match any pin. Multiple matches are ambiguous. Malformed live data makes the results incomplete. The response includes the total match count and up to 20 matches with node IDs, pin labels, and pin indices. A live MCP check identified one existing and one absent connection. Presence does not prove a new connection was created or that a signal executed.

- `showkontrol_validate_patch`: send a patch specification with `dryRun: true` for app-side validation.

- `showkontrol_get_patch`, `showkontrol_put_patch`: read or submit the whole running patch. Supply the app’s expected JSON body.

### Live graph building

- `showkontrol_plan_live_graph`: preview configured nodes and resolve local `ref` values to their final titles. Use `{node: localRef, pin?}` for a planned node and `{existingNode: ID, pin?}` for an existing live node. Connections can use either endpoint type. To validate connections between existing nodes, pass an empty `nodes` array and use `existingNode` for both endpoints. The `nodes` and `connections` arrays cannot both be empty. A live MCP dry run validated an existing-node-only connection without changing the connection list; it was not applied. The result contains `nodes` and `connections` for `showkontrol_compose_live_patch`, the mapping, and the app's dry-run result. Each preview has a `paramComparison` that reports requested parameters the app changed, omitted, or returned ambiguously. Inspect it even when the patch dry run succeeds. A live test showed that an invalid boolean was accepted by the dry run but returned as `false` in the preview; the comparison reported the mismatch. Preview node IDs are temporary and are not used in the plan. The app state can change between the dry run and a later write. A live MCP test connected an existing Player 1 node to a new group, verified the connection, then removed the group and restored the node and connection baseline. Graph execution was not verified.

- `showkontrol_create_staged_live_graph`: create up to 50 live nodes in sequence, then create up to 100 connections in sequence. Each node has a unique local `ref`, `request`, `title`, and optional `params`. Use `{node: ref, pin?}` for a new node and `{existingNode: ID, pin?}` for a live node. The tool uses the IDs returned by node creation, so nodes can have the same normalized title. It does not use preview IDs. For each supplied parameter, it checks the returned value exactly before continuing. If a value is missing, duplicated, or changed, it stops and reports the created node ID; the app may have changed the value. This changes the live show and is not atomic. If a write fails or its result is uncertain, the tool stops and returns the completed nodes and connections, the failed stage and an outcome-unknown note. HTTP 422 validation errors include a bounded message with the configured credentials redacted. Timeout and connection errors include transport details. Other internal errors use a generic message. It does not retry or roll back. Inspect the live state before further changes. A live MCP test created a trigger and two notification actions with the same title, verified both ID-based connections, then removed the nodes and restored the patch baseline. Another live test confirmed that a changed parameter produces a partial report containing the created node ID. The node was removed and the baseline restored. A successful response reports accepted writes; it does not verify graph execution.

- `showkontrol_compose_live_patch`: submit a typed live patch plan with `nodes` (each has `request`, `title`, and an optional `params` object) and `connections` (each has `from` and `to` with `node` and optional `pin`). Connections must use the actual final node titles; parameters can change a node’s title. For example, selecting `action.category: Application` and `action.t7: Feedback/Notify` produced the title `FeedbackNotify`. Metadata aliases are not supported. Parameter keys and values pass through unchanged. ShowKontrol can accept a value and return a different value. For a live write, the result preserves the app response fields and adds `parameterChecks`. A malformed non-object response is preserved in `response`. The checks compare requested values with returned nodes in request order and report missing, ambiguous, and mismatched values without repeating values. If the response or node mapping is invalid, verification is incomplete. A live MCP test detected a changed boolean in an applied temporary group; the test removed the group and restored the patch baseline. Details are limited to 100 issues, with long IDs and keys shortened. These checks do not verify execution. `dryRun` defaults to `true`; set it to `false` explicitly to submit a live change. The server sends one request and does not retry. In a live MCP test, ShowKontrol accepted a dry run, applied two group nodes and a pin 0 connection, and returned them on readback. A second live MCP test created a configured trigger and notification action with a pin 0 connection. The app renamed them to `cue_active` and `FeedbackNotify`; their settings and connection were read back. A third live MCP test created a trigger connected to a disabled OSC output at a loopback address, and read back its settings and connection. The tests removed their nodes and restored the baseline. In a loopback test, a local UDP receiver received a control datagram, but neither firing the OSC node nor firing an isolated connected trigger produced an observed OSC packet. The OSC node reported effectively stopped even with its stop parameter false; the cause remains unknown. Hardware output remains unverified. A separate dry run using a title containing spaces returned an unknown-node error; the cause is unconfirmed. Execution of the configured graphs, other output types, and other pins remain unverified.

REST calls are not retried. After a timeout, read the show state before you decide whether to repeat a write. A timeout can occur after ShowKontrol applied a change. Binary reads and event samples are bounded as described above. Live API availability and the exact patch-building request schemas depend on the app and configuration. This bridge does not validate the semantics of generic requests.

## Show files and parts

The installed app produced a `.skshow` XML wrapper with base64 parts and MD5 checksums. A modified copy passes checksum and XML checks. The complete show schema and automatic cue-graph authoring are not verified. Use test copies and check them in ShowKontrol before use.

- `showkontrol_inspect_show`, `showkontrol_read_show_part`, `showkontrol_edit_show_part_copy`: inspect the XML wrapper and its base64 parts, verify MD5 checksums, and edit one XML part in a new `.skshow` file. Untouched parts remain byte-for-byte unchanged.

- `showkontrol_inspect_show_overview`: summarize the parts, tracks, cues, set lists, patch nodes, and canonical `content/Program.skpr` items from one show snapshot without returning raw XML. Program item summaries include start, name, notes, and graph and timeline presence. They are static format evidence; application acceptance, item sorting, cues, and media are not verified. The overview rejects a Program summary over 1,000 items or 1 MiB of item JSON.

- `showkontrol_validate_show`: check checksums, node IDs, graph connections, numeric pin indices, router targets, set-track references, and direct timeline cue fields. For direct cues, `layer` must be an integer within the direct layer count, `startMs` must be finite and nonnegative, and `lenMs` must be finite and positive. Direct cue graph nodes with an explicit stored `stopped="1"` attribute or `node.stopped` setting of `true` produce a warning. The warning does not establish the active node state or why a cue did or did not run. Other stopped-state encodings are not checked. Missing cue fields and nested cues produce warnings and partial coverage. A cue with a valid numeric `layer` also produces a warning and partial coverage if the timeline has no direct `layers` element or has multiple direct `layers` elements. These checks cover the supported writer constraints, not all possible cue variants. Pin and router target checks cover supported patch and cue graphs; router targets require exactly one matching router name in patch.skf. Check the per-part coverage and diagnostic severity: scene schema validation and unsupported graph paths are reported as warnings with partial coverage. This does not check pin compatibility or prove the show will load or run.

- `showkontrol_read_show_part_page`: read a large UTF-8 show part in bounded pages. Pass the returned `sha256` and `nextOffset` to read the next page from the same source version. Offsets count UTF-16 code units.

- `showkontrol_inspect_xml`, `showkontrol_edit_xml_copy`: inspect UTF-8 XML and make exact text edits in a new file. The source checksum must match.

## Timelines and cues

- `showkontrol_inspect_timeline`: inspect the root metadata, layers, audio entries, direct audio clip attributes and cue element paths in an offline version 1 `.sktl` file. `showkontrol_inspect_show_timeline` provides the same timeline data for a show part. `audioClips` lists each direct `sktimeline/audio/clip` with its zero-based `audioIndex` and XML attributes as strings; `audio` retains the lane attributes. An app save reserialized one synthetic clip with `name`, `file`, `wave`, `grid`, `pps`, `offsetMs`, `vol`, `trimStartMs`, `trimEndMs`, `fadeInMs` and `fadeOutMs` attributes. The app cleared its source path. Playback, attribute meanings, valid values and other clip variants remain unverified.

- `showkontrol_inspect_show_timeline`, `showkontrol_add_show_timeline_cue_copy`: inspect a named `.sktl` part and add a simple cue in a new `.skshow` copy. The archive checksum must match. The tool validates part checksums and updates the changed part checksum. Other parts are preserved. ShowKontrol displayed a generated cue in a separate test session.

- `showkontrol_add_timeline_cue_copy`: add a simple cue to a new offline timeline copy. Layer indices start at zero; start and length are in milliseconds. The source checksum must match and the destination must not exist. The shape comes from an app-created cue. In a separate test session, ShowKontrol R27 27.0.11 loaded a generated copy and displayed the added cue at 5 seconds with a 2-second duration. This tool does not create an action graph.

- `showkontrol_add_show_timeline_cues_copy`: add up to 100 simple cues to a new show copy. The destination filesystem must support hard links. The operation does not create action graphs.

- `showkontrol_edit_show_timeline_cues_copy`: apply 1–100 ordered edits to cue fields across timeline parts in one new show copy. Each edit has `name`, `cueId`, and at least one of `layer`, `startMs`, `lengthMs`, or `label`. Inspect the source checksum first. Each step checks the previous copy. The tool preserves cue graphs and publishes only after all edits succeed. The destination must not exist and its filesystem must support hard links. An MCP test edited a cue in a copy of an app-saved test show and read back its unchanged graph. App acceptance remains unverified.

- `showkontrol_edit_timeline_cue_copy`, `showkontrol_delete_timeline_cue_copy`: edit or delete a cue in a new copy. Moving or editing a cue preserves its action graph. Deleting a cue with a graph requires `deleteGraph: true`. The tool checks literal references in supported XML. A standalone file check covers only that timeline. External and computed references remain unchecked. App acceptance remains unverified.

- `showkontrol_edit_timeline_layer_copy`: append, rename, move, or remove an unoccupied layer in a new timeline or show copy. Move and remove update direct cue layer indices. Unknown references outside the timeline and app acceptance remain unverified.

- `showkontrol_inspect_cue_references`: scan decoded XML show parts for literal occurrences of a cue ID and its graph node IDs outside the selected cue. Results may include unrelated text or definitions. Encoded, computed, external, and binary references are not covered; an empty result does not prove a cue is unused. The scan limits identifiers and returned records and reports truncated output.

## Audio lanes and clips

Lanes and clips have no IDs. They are selected by `audioIndex` and `clipIndex`. Get both from `showkontrol_inspect_timeline`, `showkontrol_inspect_show_timeline`, `showkontrol_inspect_program_timeline` or, in a session, `showkontrol_inspect_session_media`. None of these tools copies media, edits `media.map` or creates waveform caches; in a session directory use [`showkontrol_compose_session_media_copy`](#session-directories). Why lane names and order are treated so conservatively is explained in [Audio lane names and order](evidence.md#audio-lane-names-and-order).

- `showkontrol_add_timeline_audio_lane_copy`: add an empty direct audio lane in a new timeline or show copy. Supply an inspected SHA-256, a unique lane name, and `follow` as a boolean. Its `name` and `follow` fields follow an R27 app-saved lane. In a timeline with a direct `deck` element the lane is inserted before that deck, as before; existing lanes must precede it, and more than one deck is rejected. A timeline without a deck is accepted only in the shape of an R27 27.0.11 app-saved empty track: `<titles/>`, `<layers>` with four layers, then `<audio name="Audio 1" follow="0"/>` as the last element, with no deck. It needs exactly one direct `layers` element followed only by direct audio lanes (possibly none) up to the end of the timeline, with nothing but whitespace between them; the new lane is appended after the last lane, or directly after `layers` when there is none. Removing the lane from that empty track and adding `Audio 1` with `follow: false` restores the app-saved bytes. Other deckless layouts, such as cues or other elements after the lanes, are rejected, because where the app places a lane relative to them is not observed. The result's `audioIndex` is the new lane's index (it is always the last lane) and `position` is `before_deck`, `after_last_lane` or `after_layers`. Follow behavior, whether the app adds a deck when it next saves, and app acceptance of a deckless timeline with an added lane are unverified. Add clips with `showkontrol_add_timeline_audio_clip_copy` using the new copy and its current SHA-256.

- `showkontrol_add_timeline_audio_clip_copy`: append an audio clip to an existing direct audio lane in a new `.sktl` or `.skshow` copy. Supply the inspected source SHA-256, zero-based lane index, and all clip fields. The fields follow one R27 imported-WAV fixture. Millisecond fields and `pps` accept non-negative numeric strings; the source trim end must exceed the start. This does not copy media, update `media.map`, or generate waveform caches. The generated clip has not been opened or played in ShowKontrol. Inspect paths, dependencies, and the resulting copy before use.

- `showkontrol_edit_timeline_audio_clip_copy`: edit existing `name`, `file`, `wave`, `grid`, `pps`, `offsetMs`, `vol`, `trimStartMs`, `trimEndMs`, `fadeInMs`, or `fadeOutMs` attributes on a direct audio clip in a new `.sktl` or `.skshow` copy. Inspect the source first and provide its SHA-256. `audioIndex` selects the zero-based direct audio lane; `clipIndex` selects the zero-based direct clip within that lane. Values are strings; `name`, `file`, `wave` and `grid` follow the add-clip limits (at most 4,096 characters, no control characters). Each attribute must already exist exactly once; the tool does not add attributes or create clips. The result's `previous` gives the replaced values. Setting `file` changes the clip media. The meaning of `wave` and `grid` is unverified, and they may describe the previous media, so changing `file` on a clip whose `wave` or `grid` is nonempty requires that edit to state that attribute explicitly (its current value keeps it). The new file is not opened: format, duration against the trims and fades, waveform caches and `media.map` rows are not checked, and app relinking is unverified. An MCP test changed `offsetMs` and `fadeInMs` in a copy of the app-reserialized experimental timeline and read the values back. The source clip had an empty file path. Attribute meanings, valid values, playback, and app acceptance are not verified. Validate the copy in ShowKontrol.

- `showkontrol_remove_timeline_audio_clip_copy`: remove one direct audio clip from a new `.sktl` or `.skshow` copy. Supply the inspected SHA-256, `audioIndex`, and `clipIndex`. Only the clip element's bytes are removed; whitespace around it, other clips, unknown attributes and other parts are unchanged, and the result is parsed back to check that every other clip is intact. Later clips in the lane move down one index. The result returns the removed clip's attributes. Observed clips have no IDs; a clip, or any element inside it, with an `id` attribute is rejected because references to it cannot be checked. The tool does not delete media, change `media.map`, or remove waveform caches. App acceptance is unverified.

- `showkontrol_remove_timeline_audio_lane_copy`: remove one direct audio lane from a new `.sktl` or `.skshow` copy. Supply the inspected SHA-256 and `audioIndex`. A lane that contains clips requires `removeClips: true`; a lane that contains any other element or text, or carries an `id` attribute on itself or a clip, is rejected. A lane name that appears literally as a whole attribute value or element text elsewhere in the timeline, or in another `.skf`, `.sktl`, `.sksc`, `.skpr` or `.skcp` part of the show, is treated as a possible reference and rejected. Track names (`sktimeline` `name`), lane names, and clip names are not treated as references, so other tracks' lanes with the same name do not block removal; set lists, which name tracks and sets, are not checked. Later lanes move down one index. Whether anything refers to lanes by position, or by a computed or encoded name, is unknown. The result returns the removed lane and clip attributes. Media and `media.map` are unchanged. App acceptance is unverified.

- `showkontrol_rename_timeline_audio_lane_copy`: rename one direct audio lane in a new `.sktl` or `.skshow` copy. Supply the inspected SHA-256, `audioIndex` and `laneName`, the lane's current name; both must match, so a stale index fails instead of renaming another lane. Only the bytes of the `name` attribute value change, in the existing quote style; `follow`, clips, whitespace and every other part are unchanged, and the timeline is parsed back to check that nothing else moved. The lane must have the observed R27 shape: no attributes other than `name` and `follow`, and only clips and whitespace inside. A rename to or from `Audio 1` is refused (see [Audio lane names and order](evidence.md#audio-lane-names-and-order)). A name used by another lane of the timeline is refused, and so is an old name shared by several lanes. The old and new names must not appear literally, as a whole attribute value or element text, in the timeline or in another `.skf`, `.sktl`, `.sksc`, `.skpr`, `.skcp` or `.sktr` part of the show; track, lane and clip names are definitions and do not count. Set lists, REAPER projects and other external files are not checked. The result returns `previousName`, `laneName` and the lane attributes. App acceptance is unverified.

- `showkontrol_move_timeline_audio_lane_copy`: move one direct audio lane to `toIndex` in a new `.sktl` or `.skshow` copy. Select it with `audioIndex` and its current `laneName`. The lane elements are permuted. The whitespace between lanes stays in its slot, and every other byte is unchanged. The result's `indexMap` lists each lane whose position changed (`from`, `to`); its clips' `audioIndex` changes with it. The first lane never moves, and no lane moves into position 0. All lanes must form one uninterrupted run of sibling elements with only whitespace between them. Every lane must have only `name` and `follow`, a unique nonempty name, and only clips inside. Clips may carry only the observed fields (`name`, `file`, `wave`, `grid`, `pps`, `offsetMs`, `vol`, `trimStartMs`, `trimEndMs`, `fadeInMs`, `fadeOutMs`) and no content. A `deck` element with attributes or content is refused. So is any element name, attribute name, or `key` or `*ref*` attribute value in the timeline or another supported part (including `.sktr`) that mentions `audio`, `lane` or `video`, outside the lane and video definitions of timelines, because it may address lanes by position. A part that cannot be parsed fails the call. Whether lane order beyond the first lane changes playback, outputs, REAPER export or Program items is unverified.

## Cue graphs

- `showkontrol_inspect_cue_graph`: inspect the graph nodes, connections and settings of a cue in an offline timeline or show archive.

- `showkontrol_remove_cue_graph_copy`: remove a cue's graph in a new timeline or show copy. It preserves the cue and checks literal node references in supported XML. External and computed references and app acceptance remain unverified.

- `showkontrol_edit_cue_graph_wire_copy`: add or remove a supported pin-0 cue graph connection. Script and OSC candidate connections were accepted by R27 patch dry runs; cue loading and execution remain unverified.

- `showkontrol_edit_cue_graph_settings_show_copy`: change up to 100 existing cue graph settings across timelines, cues and nodes in one new show copy. Each `settings` item has `name`, `cueId`, `nodeId`, `key` and string `value`. Inspect the show checksum first. The batch fails if any setting is missing or ambiguous. The destination must not exist and its filesystem must support hard links. Values and app acceptance remain unverified.

- `showkontrol_edit_cue_graph_setting_copy`: change an existing node setting in a cue graph in a new copy. Inspect first. The tool does not create a missing setting. For `node.stopped`, use the exact string `true` or `false`. The tool updates all supported existing stopped representations together. Batch and compose setting edits use the same rule. Other values are not validated. ShowKontrol acceptance remains unverified.

- `showkontrol_set_cue_graph_node_stopped_copy`: change the explicit stopped state of a cue graph node in an offline timeline or show copy. It updates supported existing `stopped` and `node.stopped` representations together. It rejects missing, ambiguous, or unsupported representations. This does not prove the node will run: ShowKontrol can also stop a node for license or seal conditions. App acceptance is unverified.

- `showkontrol_add_cue_graph_setting_copy`: add a missing fixture-supported setting to a cue graph node in a new copy. Only `trigger.path`, `trigger.on` and `action.category` on their corresponding node types are supported. Values and app acceptance remain unverified.

- `showkontrol_copy_cue_graph_show_copy`: copy a graph from a cue in the same or another show to an empty cue in a new show archive. Set `sourceName` to select the source timeline and `name` for the target timeline. For a separate show, also set `template` and its inspected `templateSha256`. It supports group input, trigger, action, Script processor, and OSC generator nodes. Script and OSC use patch-derived prototypes; cue acceptance and execution are unverified. It scans target `.skf`, `.sktl`, `.sksc`, and `.skpr` XML parts for node IDs and remaps graph nodes and connections. It rejects ID-like references outside node IDs and connection endpoints, except a router target that matches exactly one valid destination patch router name. This conservative check can reject harmless text. Other external dependencies are not checked. An MCP test copied the notification graph within an app-saved test show and read back three nodes and two connections; validation reported only partial scene coverage. ### Opaque node text and stopped-node warnings

For supported cue graphs, Program item graphs, embedded Program timelines, and patch setting copies, set `allowOpaqueNodeText: true` to preserve node-like text in a scalar Script `proc.script` or OSC `gen.address` setting. For graph assembly, batch copies, and patch settings in composition, set it on each donor or copy that needs it. The tool does not rewrite that text. If the option bypasses a reference check, the result includes `opaque_node_references_unverified`; inspect the text and its dependencies. Structural references remain checked. Other copy paths may not support this option.

The direct cue graph and cue node copy tools, batch graph copy tool, and cue graph assembly tools also return a `warnings` array for copied nodes that store a stopped value. Warning scopes use the destination cue and remapped node IDs. For standalone timeline copies, `part` is the destination file path. The two compose tools return a `warnings` array from the final output timelines they edit. Each `stored_stopped_cue_node` warning identifies the part, cue, and node when IDs are present. It reports a stored `stopped="1"` attribute or `node.stopped` setting of `true`. It does not establish the active node state or its effect on execution. The scan uses the same direct cue graph scope as show validation. A scan failure prevents publication. Cleanup warnings are separate.

## Tracks and set lists

- `showkontrol_create_show_track_copy`: add an empty track using an inspected empty timeline template. The set list is unchanged. ShowKontrol R27 27.0.11 loaded a generated test show and displayed the new track in its catalog; playback and other track variants remain unverified.

The tool rejects literal references in supported XML, including set lists. Remove those references first. It does not check external, binary, or computed references. Application acceptance is unverified.

For track creation or composition, an external empty template can be supplied as `templateDonor` with `file`, `format` (`sktl` or `skshow`), and inspected `sha256`. - `showkontrol_rename_show_track_copy`: rename a unique timeline and all exact matching entries in supported version 2 set lists in a new offline show copy. An MCP test on an app-saved show updated the timeline and matching set-list entry while preserving other parts and valid checksums. Unsupported literal references in supported XML block the rename. - `showkontrol_inspect_show_setlist`, `showkontrol_add_show_setlist_track_copy`: inspect sets and append an existing track to a set in a new show copy. App acceptance remains unverified.

Empty-set behavior, active-set behavior, and ShowKontrol acceptance are unverified.

- `showkontrol_edit_show_setlist_copy`: create, remove, or move a set, remove a track entry, or change the order of track entries in a new show copy.   `move_set` takes `setName` (a name that occurs exactly once) and `toIndex`, the set's zero-based position in the resulting order; `index`, `newSetName`, and `allowContentRemoval` are rejected, and a move to the set's current position is rejected as no change. A set list without a plain decimal `active` value inside the set range is rejected, because which set should stay active is then unknown. Whether anything refers to a set by position, whether ShowKontrol shows the new order, and how the app itself renumbers `active` when a set is dragged are unverified. ### Clone a media-backed timeline

`showkontrol_clone_media_track_copy` takes `source`, `destination`, the SHA-256 from inspection, `templateName` (the exact `.sktl` part in that same show), a unique `trackName`, and a unique `partName`. It creates a new show file. It copies the selected timeline's media attributes, audio and other non-cue XML. It removes direct cues and their graphs from the clone. The original part and set list stay unchanged. It rejects nested cues, unsupported graph or identity structures, literal references to removed IDs, duplicate names and corrupt parts. It checks the source hash again before publication and does not overwrite the destination. Set `cueMode` to `copy` to retain direct cues and their graphs. The tool assigns fresh cue and node IDs, rewrites connection endpoints, and returns `cueMapping` and `nodeMapping`. It rejects unsupported identity fields, ambiguous graphs, and references it cannot safely rewrite. By default, it rejects opaque node text that contains node-like references. Set `allowOpaqueNodeText: true` to copy supported opaque settings unchanged. The result gives a warning for each affected setting, with the new part, cue and node IDs. References in that text are not verified or remapped. Other unsupported references still cause an error. ID scope and application playback remain unverified.

This is an offline XML operation. The tool does not check media files, encoded or external references, ShowKontrol acceptance, or playback. Inspect and test the copy in ShowKontrol before use. Synthetic tests do not establish application compatibility.

Composition also accepts `mediaClone: {templateName, cueMode?, allowOpaqueNodeText?}` with `trackName` and `partName`. It selects a timeline in the current show and cannot be combined with `existingPartName`, `templateName`, or `templateDonor`. The clone preserves media and audio fields. `cueMode` defaults to `remove`; `copy` remaps direct cue and graph node IDs. The returned `mediaClone` receipt includes `cueMapping` and `nodeMapping`, which record the initial clone even if later edits remove a cue. The source must have a root media field or an audio clip; a mediaWave-only timeline is not supported. Copy mode rejects opaque node-like text by default. Set `allowOpaqueNodeText: true` to copy supported opaque settings unchanged and receive scoped warnings. Other unsupported references still cause an error. Composition reports warnings for affected settings that remain in the final show. Media, external references, playback, and ShowKontrol acceptance are not verified.

For a clone with `cueMode: "copy"`, use `sourceCueId` in `cueRemovals` and `cueEdits`, and use both `sourceCueId` and `sourceNodeId` in `graphSettingEdits`. These select IDs from the source timeline through the clone receipt. Direct `cueId` and `nodeId` selectors remain for existing timelines and are rejected for clones. Clip edits, new cues, and a set-list entry can be added to a clone. In full composition, staged Program `cueIndex` selects only newly added cues; it does not select copied cues. Use `graph.stagedShow: {trackIndex, sourceCueId}` to select a copied cue from a clone in the same full composition. The selector fails if the cue was removed or has no mapping. The entire composition rolls back if an operation fails.

## Composition

The compose tools apply many edits in one transaction and publish only when every step succeeds. `showkontrol_compose_full_show_copy` is the broadest offline entry point; `showkontrol_compose_session_media_copy` accepts the same inputs for a session directory with media (see [Session directories](#session-directories)).

- `showkontrol_compose_show_copy`: create a track, add cues, optionally copy supported graphs from donor shows, and optionally add the track to an existing set. Each cue can choose a donor or omit its graph. Optional cue `settings` entries contain `nodeId`, `key`, and `value` strings. Use a node ID from the selected donor graph and the key of an existing setting. The copy uses the new node ID and applies the value to that cue. Settings require a graph. A cue can instead specify `mixedGraph` with `nodes` and `wires`, using the same node and wire format as `showkontrol_assemble_mixed_cue_graph_show_copy`. A mixed graph overrides the track default donor; do not also specify a cue donor. For a mixed graph, each `settings` entry uses a zero-based `nodeIndex` in place of `nodeId`. Optional `patchSettings` entries copy an existing setting from an app-saved patch node, adding it to the cue node or replacing its existing setting. Each entry has the target `nodeId` (or `nodeIndex` for a mixed graph), `template` (an absolute path), `templateFormat` (`skf` or `skshow`), `templateSha256`, `templateNodeId`, and `key`. These entries run after `settings`, in array order. The patch node and cue node types must match. The existing patch-setting reference checks apply; values, dependencies, and ShowKontrol acceptance remain unverified. The result includes `nodeIds` in the same order as `nodes`. Inspect every source first. The operation creates an offline copy and requires hard-link support. It can add fixture-shaped audio lanes and clips, but does not copy media or update media mappings. ShowKontrol opened a fresh test session containing a composed archive and extracted its timeline and set-list parts unchanged. In a separate session using those parts, the app displayed the track, its two cues, and its set-list position. A generated cue with a notification action executed in a separate test; other graphs remain unverified.
  Optional `layerOperations` run in order after track creation and before cues. Each entry has `operation` (`append`, `rename`, `move`, or `remove`) and `layerName`. Append and rename use `newName`; move uses a zero-based `targetIndex`. Append copies an empty named layer to the end. Move and remove update direct cue indices; removal rejects occupied layers. Cue `layer` values are zero-based indexes in the resulting layer list. The layer operations have not been verified in ShowKontrol.
  Optional cue `postPatchSettings` use the same node selector, key, and value format as `settings`. They run after `patchSettings`, so a copied setting can be customized in the same transaction. Values, dependencies, and app acceptance remain unverified.
  Set `set.createIfMissing` to `true` to create the named set if it is absent. An existing unique set is reused. Duplicate set names cause an error. If omitted or false, the set must already exist. Set creation and track composition are published together; a failure leaves no destination file. In a multi-track composition, later tracks can reuse the set created by an earlier track.

For either compose tool, `cues` may be omitted or empty. Creating a track is sufficient; an existing track must have at least one new cue, layer operation, audio clip edit, audio clip or lane removal, cue removal, cue edit, or graph setting edit. Edit-only composition has not been validated in ShowKontrol. A failed operation leaves no destination copy. For either compose tool, choose one track mode. To create a track, supply `templateName`, `trackName`, and `partName`, as before. To add cues to an existing timeline, supply `existingPartName` with the exact timeline part name. Do not supply the three new-track fields or `set` in this mode. Optional layer operations, donors, mixed graphs, and cue settings apply to the selected timeline. Existing media, cues, and other parts are preserved by the offline writers. The result identifies this mode with `existingPartName`. This mode has not been validated in ShowKontrol. Each track may include `cueRemovals`, an ordered array of up to 100 `{cueId, deleteGraph?}` entries for existing tracks. Removals run after layer and audio clip edits, before cue edits, graph setting edits, and new cues. Set `deleteGraph: true` to remove a cue with a graph. Literal references in supported show XML are checked. External and computed references remain unchecked. Validate the copy in ShowKontrol. Each track may include `cueEdits`, an ordered array of up to 100 `{cueId, layer?, startMs?, lengthMs?, label?}` entries. Each entry must change at least one existing field. Edits run after layer and audio clip edits and before new cues. They preserve existing cue graphs. New tracks contain no existing cues, so nonempty `cueEdits` require `existingPartName`. This capability has not been validated in ShowKontrol. A failed edit leaves no destination copy. Each track may include `graphSettingEdits`, an ordered array of up to 100 `{cueId, nodeId, key, value}` entries for existing cue graphs. These edits run after cue edits and before new cues. They require `existingPartName` and an existing setting on the specified node. Inspect the graph first. Values and ShowKontrol acceptance remain unverified. A failed edit leaves no destination copy. Each track may include `audioClipEdits`, an ordered array of up to 100 `{audioIndex, clipIndex, attributes}` entries. Indices select zero-based direct audio lanes and their direct clips. Each `attributes` object contains one or more existing attributes accepted by `showkontrol_edit_timeline_audio_clip_copy`, with string values. Edits run after track selection, layer operations and audio adds, before cues. New-track templates cannot contain clips, so nonempty edits require an existing timeline or a `mediaClone` with clips. Inspect the timeline first. The values and ShowKontrol acceptance remain unverified. A failed edit leaves no destination copy. Each track may also include `audioClipRemovals`, up to 100 `{audioIndex, clipIndex}` entries, and `audioLaneRemovals`, up to 100 `{audioIndex, removeClips?}` entries, with the checks of the two removal tools. Indices in edits, removals and clip `audioIndex` selectors all refer to the timeline as it was before the track's audio operations: added lanes and clips are appended and do not shift them, and removals run last, clips before lanes, each from the highest index down. The track receipt reports `audioClipEdits` with previous values, `audioRemovals` with the removed clip and lane attributes in request order, and `audioLanes` with each added lane's final `audioIndex`. A selector that is out of range, repeated, both edited and removed, removes a clip inside a removed lane (use `removeClips`), or adds a clip to a removed lane fails before any change. Removals have not been validated in ShowKontrol. Each track may also include `audioLaneOperations`, up to 100 ordered `{operation: 'rename', audioIndex, laneName, newName}` or `{operation: 'move', audioIndex, laneName, toIndex}` entries with the checks of the two lane tools. They run after every other audio operation of the track, including removals; each `audioIndex` addresses the lanes as the previous step left them, starting from the final indices of the audio stage (an added lane's `audioIndex` in the receipt before moves). The receipt's `audioLaneOperations` lists one entry per operation (`previousName` and `laneName` for a rename, `fromIndex`, `audioIndex` and `indexMap` for a move), and `audioLanes` reports each added lane's final `audioIndex`, with `finalLaneName` when it was renamed. A lane operation alone is enough for an existing track. A failed operation publishes nothing. Renamed and moved lanes have not been opened in ShowKontrol.

- `showkontrol_compose_multi_track_show_copy`: compose up to 20 new or existing tracks in one offline copy using the same track and cue options. Each track selects its own mode. Ordered `setlistOperations` run after track composition and support `create_setlist`, `append_track`, `create_set`, `remove_set`, `move_set`, `remove_track`, and `move_track`. Track indices are zero-based. Removing a populated set requires `allowContentRemoval: true`; the last set cannot be removed. `move_set` takes `name`, `setName`, and `toIndex` and follows `showkontrol_edit_show_setlist_copy`; each operation sees the order left by the previous one, so a set created earlier in the list can be moved. The same operations are available in `showkontrol_compose_full_show_copy` and `showkontrol_compose_session_media_copy`. App acceptance is unverified. At least one change is required; tracks may be empty when operations change the show. Optional `patchOperations` use the ordered operations and restrictions of `showkontrol_edit_patch_batch_copy` before track composition. Node removal checks the patch and supported `.skf`, `.sktl`, `.sksc`, `.skls`, and `.skpr` show parts for ID text. It can reject harmless text. Other parts and external references are not checked. Copied nodes retain internal references and do not include connections or dependencies. Patch values, compatibility, and ShowKontrol acceptance are not validated. It does not author media and requires hard-link support. This multi-track operation remains unverified in the app.

- `showkontrol_compose_show_copy` and `showkontrol_compose_multi_track_show_copy` accept `audioLanes` and `audioClips` for each track. Each added lane has `laneName` and `follow`. Each clip selects either an existing `audioIndex` or a `laneName` added in that composition, and supplies the clip fields used by `showkontrol_add_timeline_audio_clip_copy`. Lanes are added before clips; the composition publishes only after all edits succeed. These tools do not create media files, `media.map` rows, or waveform caches; use `showkontrol_compose_session_media_copy` for a saved session directory. App acceptance and playback remain unverified.

### Full show composition

`showkontrol_compose_full_show_copy` combines patch, track, set-list and optional Program creation in one offline transaction. It publishes a new show copy only after all stages and validation succeed. Program timeline donors can use `stagedShow: {trackIndex}` to select a track created or edited earlier in the transaction. A Program graph donor can use `stagedShow: {trackIndex, cueIndex}` for a newly created cue, or `{trackIndex, cueId}` for an existing cue. Track and cue indices use the input order. External donors use the same paths and checksums as the Program composer. Inspect the returned mappings and validation warnings. Media, external dependencies, runtime behavior, and ShowKontrol acceptance remain unverified.

For a staged Program graph, each setting can select a donor node by `nodeIndex` in the staged cue graph instead of a generated `nodeId`. For example, set `trigger.path` to `item.active` on the trigger node when the item activity signal is needed. Inspect the donor graph and its node order first. Trigger behavior remains unverified.

For a staged Program timeline, each setting can use `cueIndex` and `nodeIndex` to select a newly created cue and a node in its staged graph. Alternatively, supply both `cueId` and `nodeId` for an existing cue. Do not mix the two selector forms. Cue indices follow the input track's new-cue order; node indices follow the inspected staged graph's node order.

The deckless shape was observed in an app-saved track, not in an app-saved Program item timeline; it reaches an item when such a track is embedded as its timeline. Whether ShowKontrol accepts a deckless Program item timeline, with or without an added lane, is unverified.

- `add_timeline_audio_clip` (`index`, `audioIndex`, `clip`) follows `showkontrol_add_timeline_audio_clip_copy` and requires every clip field.

- `edit_timeline_audio_clip` (`index`, `audioIndex`, `clipIndex`, `attributes`) follows `showkontrol_edit_timeline_audio_clip_copy`. Changing `file` on a clip with a nonempty `wave` or `grid` requires restating them.

- `remove_timeline_audio_clip` (`index`, `audioIndex`, `clipIndex`) follows `showkontrol_remove_timeline_audio_clip_copy`.

- `remove_timeline_audio_lane` (`index`, `audioIndex`, optional `removeClips`) follows `showkontrol_remove_timeline_audio_lane_copy`.

- `rename_timeline_audio_lane` (`index`, `audioIndex`, `laneName`, `newName`) follows `showkontrol_rename_timeline_audio_lane_copy`. The old and new names are also checked in the whole staged Program, including other items' notes and graphs, and in every other supported part of the show.

- `move_timeline_audio_lane` (`index`, `audioIndex`, `laneName`, `toIndex`) follows `showkontrol_move_timeline_audio_lane_copy`, including the first-lane rule. The whole staged Program and every other supported part are also checked for fields that mention audio, lanes or video. The receipt has `fromIndex`, the new `audioIndex` and `indexMap`.

Lanes and clips have no IDs, so they are selected by position. `index`, `audioIndex` and `clipIndex` all address the state after earlier operations in the list. A new lane can receive clips in a later operation through its returned `audioIndex`, which is the existing lane count. Removing a clip or lane moves later clips or lanes down one index. Get the starting indices from `showkontrol_inspect_program_timeline`. A clip or lane carrying an `id` attribute cannot be removed. When a lane is removed, its name is checked as a possible literal reference in the whole staged Program and in every other `.skf`, `.sktl`, `.sksc` and `.skcp` part of the show. The check matches whole attribute values and element text, such as an item's `notes`, an item graph setting, or a cue label. Track names, item timeline names, lane names and clip names, including lanes of the same name in other items, are definitions and do not block removal. An item `name` equal to the lane name does block it. Set lists are not checked.

The result's `audioOperations` lists one receipt per audio operation. Each receipt has its `operationIndex`, `itemIndex`, `audioIndex`, any `clipIndex`, a lane addition's `position`, and the added, changed (`attributes` and `previous`) or removed attributes, all as they were when that operation ran. A later item removal or addition can change `itemIndex`, so re-inspect the result for final positions. These operations do not copy media or change `media.map`. In a session, use `showkontrol_compose_session_media_copy`. Program item clip playback and media resolution have not been observed in ShowKontrol.

Use `edit_timeline_graph_wire` with the current item `index`, `cueId`, `operation` (`add` or `remove`), `fromNode`, and `toNode` to edit a supported pin-0 wire in an existing cue graph. The supported node and wire types come from the observed fixtures. Other pins, external dependencies, and ShowKontrol execution remain unverified.

Use `edit_timeline_graph_wire_mapped` to wire a node copied earlier in the same Program edit. Each `from` or `to` endpoint is either `{nodeId}` for an existing node, `{nodeFromOperation}` for an earlier node-copy operation, or `{graphFromOperation, nodeIndex}` for an earlier assembled graph. The operation checks that the receipt is still active and belongs to the selected cue.

Use `copy_timeline_cue_node` to add a supported node from an inspected cue or patch donor to an existing Program cue graph. Supply `donorType`, `donor`, `donorSha256`, and `donorNodeId`; cue donors also require `donorName` and `donorCueId`, while patch donors require `donorFormat`. The result returns the new node ID. Use `edit_copied_timeline_node_setting` with `nodeFromOperation` to edit that node in the same transaction. Use `remove_timeline_cue_node` to remove an unreferenced node. Copied nodes have no wires. External and computed references and app execution remain unverified.

Use `copy_patch_setting_to_timeline_cue` to copy an existing setting from an inspected patch node into a same-type Program cue node. Select the cue with `cueId` or `cueFromOperation`, and the node with `nodeId` or `nodeFromOperation`. Supply the donor path, format, SHA-256, node ID, and setting key. An existing setting is replaced. Router targets are checked against the destination patch; action compatibility and execution remain unverified.

To select a node from an earlier graph assembly, use `graphFromOperation` and `nodeIndex`. To select one from an earlier whole-graph copy, use `copiedGraphFromOperation` and `copiedGraphDonorNodeId`. Supply exactly one node selector. The patch donor's `donorNodeId` is a separate field.

For `copy_timeline_cue_node` and `edit_timeline_graph_wire_mapped`, select the cue with either `cueId` or the zero-based `cueFromOperation` index of an earlier `add_timeline_cue`. A new cue must first have a graph. Then a later operation can copy and wire nodes into it.

For an item timeline, `settings` can contain ordered `{cueId, nodeId, key, value}` entries. Use the IDs from the donor timeline. The tool edits a private donor copy before it remaps IDs and embeds the timeline. The total limit is 100 timeline and item-graph setting edits per composition.

### Standalone Program and archive tools

`showkontrol_inspect_program` reads a standalone `.skpr` file and returns its SHA-256 and items in file order. `showkontrol_create_program_copy` creates an empty Program when given only a new destination. To create a schedule in one call, supply `items` with up to 1000 objects containing `start`, `name`, and `notes`. The tool writes the items in the supplied order. Do not combine `items` with a source or operation. The destination must be a new absolute `.skpr` path. The tool validates all items before it publishes the file and does not overwrite an existing file. For an edit, supply the source, its inspected SHA-256, a new destination, and one operation: `add`, `edit`, or `remove`. Item indices are zero-based and use file order. Authored start times are integer local milliseconds since midnight, from 0 through 86399999. Inspection also accepts decimal times in that range and retains their original text during unrelated edits. Names and notes are strings of at most 4096 characters. Removal of an item with a graph or timeline requires `allowContentRemoval: true`. Edits preserve the item's graph and timeline XML. The tools reject unsupported structures.

`showkontrol_inspect_program_item_graph` reads an item's graph from a standalone `.skpr` or a show's canonical Program part. Supply the inspected source SHA-256 and zero-based item index. The result includes node attributes, settings and connections. The tool rejects unsupported or ambiguous graph structures and output larger than 1 MiB. Graph behavior, dependencies and ShowKontrol acceptance are unverified.

`showkontrol_inspect_program_timeline` reads an item's embedded timeline from a standalone Program or a show's canonical Program part. Supply the source SHA-256 and zero-based item index from inspection. The result includes cue, layer, audio, and clip attributes; each clip has its zero-based `audioIndex` and its `clipIndex` within that lane, as used by the Program audio operations. It omits preview attributes and rejects results larger than 1 MiB. This static inspection does not verify application acceptance or media playback.

`showkontrol_extract_program_timeline_copy` copies an item's exact embedded version 1 timeline element to a new absolute `.sktl` file. Supply the standalone `.skpr` or `.skshow` source, its inspected `sha256`, and the zero-based item `index`. The destination must not exist and its filesystem must support hard links. The copy has no added XML declaration or byte-order mark. Media is not copied and IDs are not remapped. External references, media, runtime IDs, and application acceptance are unverified.

`showkontrol_edit_program_item_graph_setting_copy` changes an existing direct node setting in one item graph in a new standalone `.skpr` copy. Supply the inspected source SHA-256, zero-based item index, node ID, setting key and string value. The destination must not exist and publication requires hard-link support. After copying a cue graph, `trigger.path` set to `item.active` is a candidate for an item trigger; `trigger.on` can remain `State On` for onset. This is a static inference, and automatic trigger behavior is unverified. Inspect stored stopped states and dependencies. For `node.stopped`, use `true` or `false`; the tool also updates an existing supported `stopped` attribute. Values and ShowKontrol acceptance are unverified.

`showkontrol_copy_program_item_graph_copy` copies one direct cue graph from a standalone `.sktl` or a `.skshow` to an item in a new standalone `.skpr` file. Supply the inspected Program `source` and `sha256`, zero-based item `index`, `donor`, `donorSha256`, and `donorCueId`. For a show donor, also supply the exact `donorName` timeline part name. The destination must be a new absolute `.skpr` path. Set `replaceExisting: true` to replace an existing item graph. The tool preserves the graph XML and the item's timeline and attributes. It does not change IDs or trigger settings. Inspect the trigger settings and change `cue.active` to `item.active` as appropriate. Inspect dependencies and IDs for collisions and validity. Graph structures and application acceptance are unverified. Publication requires hard-link support.

`showkontrol_remap_program_item_graph_copy` allocates new node IDs for one item graph against an inspected target show and the source Program. Supply the source Program and target show paths and their SHA-256 values, the item index, and a new absolute `.skpr` destination. It updates direct node IDs and wire endpoints and rejects unsupported references. It cannot repair duplicate IDs already used elsewhere in the source Program. Runtime ID behavior and application acceptance are unverified.

`showkontrol_copy_remapped_program_item_graph_copy` copies a donor cue graph into a Program item and assigns fresh node IDs before insertion. Supply the inspected Program, donor and target show paths and their SHA-256 values, item index, donor cue ID, and a new absolute `.skpr` destination. For a show donor, supply its timeline part name as `donorName`. Set `replaceExisting: true` to replace a graph. The tool rejects unsupported references. Inspect trigger settings and dependencies. Runtime ID behavior and application acceptance are unverified.

`showkontrol_embed_program_timeline_copy` embeds a timeline root in one item of a new standalone Program copy. Supply the inspected Program `source` and `sha256`, zero-based item `index`, `donor` and `donorSha256`. The donor can be a standalone `.sktl` or a `.skshow`; for a show, also supply its exact `donorName` part name. The destination must be a new absolute `.skpr` path. Set `replaceExisting: true` to replace an item timeline. This uses static format evidence only; application acceptance is unverified. It does not copy media or remap IDs. An MCP test embedded an app-saved timeline and inspected its three cues and four layers; the generated Program was not opened in ShowKontrol. External references, media, and runtime IDs are unverified; the application may change node IDs.

`showkontrol_embed_remapped_program_timeline_copy` embeds a donor timeline and assigns fresh cue-graph node IDs against an inspected target show and source Program. Supply their paths and SHA-256 values, the donor and its SHA-256, the item index, and a new `.skpr` destination. Set `remapCueIds: true` to assign fresh cue IDs when reusing a timeline. The tool rejects unsupported references and returns the ID mappings. Media is not copied. External dependencies, runtime ID behavior, and ShowKontrol acceptance remain unverified.

`showkontrol_inspect_show_program` inspects the canonical `content/Program.skpr` part in an offline `.skshow`. Use `showkontrol_extract_show_program_copy` with the inspected archive SHA-256 to extract its exact bytes to a new standalone `.skpr` file. Edit that file with `showkontrol_create_program_copy`. Use `showkontrol_attach_show_program_copy` to attach the edited Program to a new archive copy. Supply the inspected archive SHA-256 and Program SHA-256. Set `replaceExisting: true` to replace an existing Program. These archive tools check all part checksums and reject duplicate names. Extraction and attachment preserve Program bytes; attachment preserves unrelated parts. Destinations must not exist and publishing requires hard-link support. ShowKontrol application acceptance is not verified.

Show validation checks direct Program graph node IDs, wire endpoints, and numeric pin fields. It also checks cue timing, layers, and supported cue graph structure in embedded timelines. Coverage remains partial. It does not prove pin compatibility or runtime behavior.

### Edit a schedule step by step

To edit a schedule in a show copy:

1. Inspect the show and its Program. Extract the Program, or create one if it is absent.
2. Inspect the Program. Add or edit items by file-order index. Use the current SHA-256 for each copy.
3. If an item has a timeline, extract it. Edit and inspect the timeline copy. Embed it in a new Program copy.
4. If an item needs a graph, copy a cue graph. Inspect its node settings, stopped state, dependencies, and IDs. Set `trigger.path` to `item.active` when the item activity signal is needed. This trigger behavior is unverified.
5. Inspect the final Program. Attach it to a new show copy with the current show and Program hashes. Inspect and validate the result.

The checks do not prove that the Program loads or runs. Media, runtime IDs, trigger behavior, and connected equipment require application tests.

## Media and sessions

This section has three parts. [Show media maps](#show-media-maps) covers `media.map` inside a single `.skshow`. [Session directories](#session-directories) covers a saved session folder with `session.skshow`, `media.map` rows and `MEDIA/` sidecar files. [Session staging](#session-staging) covers the directories a killed session call leaves behind.


`showkontrol_compose_session_media_copy` writes a new session directory. It contains the composed `session.skshow`, new `media.map` rows, verified `MEDIA/` copies of existing and new sidecars, and the source session's working files, rewritten where they are exact extractions of changed archive parts. It accepts the tracks, patch, set-list and Program inputs of `showkontrol_compose_full_show_copy`, so one call can compose a complete show with new media into a session, and it does not publish a composed session that fails show validation. It fails rather than keep working state that disagrees with the composed archive. It does not modify the source session. Existing audio clips can be re-pointed to new or mapped media (`audioClipEdits` with `mediaIndex` or `file`), and clips and lanes can be removed (`audioClipRemovals`, `audioLaneRemovals`). Ordered Program edits can add, edit and remove lanes and clips in existing Program item timelines, and their clip additions and edits also accept `mediaIndex`. `media.map` rows and sidecars are kept unless `mediaMapOperations` removes or re-points a row, and rows no clip names any more are reported. A row can be removed or re-pointed only when nothing in the composed archive or in a carried working file still names a value that leaves the map; a sidecar left without a row is kept or omitted as `removedSidecars` says. `showkontrol_inspect_session_media` lists the lanes and clips with their mapped sidecars, and the `MEDIA/` files no row names. ShowKontrol has not opened or played a generated session; see [Session directories](#session-directories) for limits.

The new session is published with a no-replace rename (`renameat2` `RENAME_NOREPLACE` on Linux, `renamex_np` `RENAME_EXCL` on macOS) when the running Node.js provides the experimental `node:ffi` module and a probe on the destination volume confirms that the rename refuses an existing directory. Node.js 26.1.0 through 26.8.1 provide `node:ffi` only when started with `--experimental-ffi` (see [Atomic session publication](setup.md#atomic-session-publication)); the server does not add the option. Otherwise it falls back to a `mkdir` claim and rename, which another process can still race; the result's `publication` says which method was used and why. Set `requireAtomicPublication` to refuse the fallback. A killed call leaves a `.showkontrol-session-staging-*` directory with an owner record beside the destination. `showkontrol_find_session_staging` reports which ones are verifiably stale, and `showkontrol_remove_stale_session_staging` removes only those, after moving each to a `.removing-` name and checking that it is still the verified directory.

`showkontrol_preflight_session_audio` checks the media behind every track and Program audio clip in a session without writing. For each clip it reports the mapped `MEDIA/` sidecar and the clip's `file` as a path on this computer: whether each opens as a readable regular file, which clips share a file, and the ffprobe duration of the opened file within a shared time budget. Missing ffprobe, failed probes and an exhausted budget stay `unavailable`, `unknown` or `not_checked`. Trim attributes are returned as stored and are not compared with duration, because one app-saved import does not establish their unit and meaning. Which candidate ShowKontrol uses, and playback, are not verified.

### Show media maps

- `showkontrol_inspect_show_media`: read one offline show snapshot and report literal `media.map` rows, exact matching archive parts and their MD5 status, timeline media fields, and direct audio clip attributes from track and Program item timelines. Program entries include an item index. Clip `clipIndex` is zero-based within its audio lane. `attributeMappings` reports exact matches between attributes and map rows; it does not establish a media link. `timelines` reports the root media fields found in the app-saved empty track fixture. Each value has a character length; values longer than 4,096 characters are omitted. The meaning of nonempty values has not been verified in the app. Each timeline and clip has `attributeMappings`: the names of attributes whose decoded values exactly match a source or archive path in `media.map`, with the matching line numbers. Matches are case-sensitive. For compatibility, a clip's `mappingLines` still reports matches for its `file` attribute only. Clip `mappingLines` lists rows whose source or target exactly equals the clip's `file` attribute. Each `timelines` entry also has `lanes`, one per direct audio lane with its `audioIndex`, attributes and `clipCount`. Duplicate or malformed rows and unreadable parts produce diagnostics. Duplicate archive part names are returned as separate matches. A saved show had a UTF-8, tab-separated source-to-`MEDIA/` mapping, but its target was not an archive part. An absent match does not establish that media is missing or unplayable. The tool does not inspect external files or test playback. It rejects large inventories and uses the offline show size limit.

- `showkontrol_add_media_mappings_copy`: append up to 100 rows to the `media.map` of an offline show, or create the `media.map`, and write a new show copy. Supply `source`, a new absolute `destination`, `sha256` from `showkontrol_inspect_show_media`, and `mappings`, each with `sourcePath` and `archivePath`. A row is written literally as `sourcePath`, a tab, and `archivePath`. `sourcePath` must be a normalized absolute path without control characters; it is not opened and need not exist. `archivePath` must be `MEDIA/` followed by one file name that passes the sidecar name rules of `showkontrol_compose_session_media_copy` (no slashes, colons, leading dot or control characters; at most 255 bytes). The tool rejects a source that is already mapped or repeated in the call, and an `archivePath` that, compared without case after Unicode normalization, equals a mapped sidecar or another new row, or names a directory that holds a mapped sidecar. Mapping a second source to an existing sidecar is therefore not supported. A show with more than one `media.map` part, or whose map is invalid, malformed or maps one source twice, is rejected; an existing map in which several sources share a sidecar is accepted, as in session copies. A show without a `media.map` part is rejected unless `createMediaMap` is `true`. `createMediaMap` with an existing map is rejected, so a caller that expected a map never gets a new one and an existing map is never replaced. Creation is also rejected when another part's last name segment, compared without case after trimming and NFKC normalization, is `media.map` (for example `Media.map`, `content/media.map` or `MEDIA/media.map`), because it would be unclear which part holds the map. A created map holds only the new rows, as UTF-8 without a byte order mark, with LF after every row, and is added as the last part of the wrapper. That is how `showkontrol_compose_session_media_copy` creates the part. No app-saved file in the repository shows where ShowKontrol places `media.map` or how it ends its lines, and whether ShowKontrol reads a map added to a show that had none is unverified. The result's `mediaMap` gives `created`, `rowsBefore` and `rowsAfter`. The new rows follow the existing ones and use CRLF when the map already does; a byte order mark and the existing rows are kept. Every other part and the wrapper text stay byte-identical; a created part is inserted just before the wrapper's closing tag, and removing it gives back the source bytes. The copy is staged beside the destination, read back with the media inventory, and published with a hard link, so an existing destination is never replaced and the destination filesystem must support hard links. For each new row the result reports its `line`, the exact `MEDIA/` archive parts with that name, and the audio clips whose `file` equals `sourcePath` (track `part`, or Program `itemIndex`, with `audioIndex` and `clipIndex`). Empty lists do not mean the mapping is wrong: a session keeps sidecars as files beside `session.skshow`, not as parts. No media file is read or copied and no sidecar or archive part is created. The copy is not validated with `showkontrol_validate_show`; only `media.map` changes. Use `showkontrol_compose_session_media_copy` to add media to a session directory, because a `session.skshow` edited with this tool has no matching sidecar. Whether ShowKontrol loads, relinks or plays a mapping added this way is unverified.

- `showkontrol_edit_media_mappings_copy`: remove or re-point existing `media.map` rows of an offline show and write a new show copy. Supply `source`, a new absolute `destination`, `sha256` from `showkontrol_inspect_show_media`, and 1 to 100 `operations`. Each operation selects one row by its `line` and exact current `sourcePath` and `archivePath`, as the inventory reports them. A missing line, a value that differs, a line selected twice, a show without exactly one `media.map` part, and a map that is invalid, malformed or maps one source twice fail before anything is written. `remove_mapping` deletes the row. `repoint_mapping` sets `newSourcePath` (a normalized absolute path), `newArchivePath` (`MEDIA/` and one file name, following the sidecar name rules), or both. A new value must not be used anywhere in the inspected map, including by a row the same call removes, and must differ from every other new value; sidecar names are compared without case after Unicode normalization. The tool therefore cannot alias a row to another sidecar, swap values, or reuse a removed value; make such changes in separate calls.

  A value that leaves the map must not be referenced elsewhere. The values checked are the source path and `MEDIA/` path of a removed row, and the old value of a re-pointed column, unless another remaining row keeps that exact value. The search covers the media fields and lane attributes of every track and Program item timeline, every attribute of every direct audio clip, and the text of every other part except `media.map` and `MEDIA/` payloads. In XML parts, attribute values, text, CDATA, comments and processing instructions are searched with entities decoded; other parts are searched as text, also with entities decoded. A value is found in its literal and URI-encoded forms, in either Unicode normalization, compared without case. A match counts only when it is not continued by a path character, so `/Music/kick.wav` is not found in `/Old/Music/kick.wav` or `/Music/kick.wav.bak`. Slashes, white space, quotes and value-delimiting punctuation are boundaries. The first referenced value fails the call with up to five locations, such as `content/T.sktl audio 0 clip 0 file`, `content/Program.skpr item 1 audio 0 clip 0 file` or `part Set.skls`. An archive part that is not UTF-8 text or fails its MD5 check also fails the call, because it cannot be searched.

  Selected rows are removed or rewritten in place; every other row keeps its bytes and line break, and a byte order mark is kept. If every row is removed, the part is kept with no rows and a `media_map_empty` warning is reported. Every other part and the wrapper stay byte-identical. The copy is staged beside the destination, read back with the media inventory, and published with a hard link, so an existing destination is never replaced. `operations` returns each row before and after, with its new line; later rows move up after a removal. `MEDIA/` archive parts are never removed; `unmappedArchiveParts` lists those no row names any more, with `reason` `mapping_changed` or `unmapped_in_source`. No media file is read. The copy is not validated with `showkontrol_validate_show`. In a session directory use `mediaMapOperations` of `showkontrol_compose_session_media_copy`, which also handles the sidecar files.

  Limits: references are found only as literal strings in the forms above. A reference by file name alone, by a relative path other than the `MEDIA/` path, through a symlink or another spelling of the same file, or in another encoding is not detected. Whether ShowKontrol resolves clips through `media.map` at all, needs a row that no part names, accepts an empty or edited map, or relinks a re-pointed row is unverified. The only app evidence is one R27 session whose `media.map` mapped original absolute paths to `MEDIA/` sidecar files.

### Session directories

- `showkontrol_inspect_session_media`: inspect `session.skshow` in an absolute session directory and report whether each mapped `MEDIA/` sidecar is a regular file, missing, unsafe, a symlink, or inaccessible. It checks metadata without reading media contents or following sidecar symlinks. It does not prove that ShowKontrol uses a file, that media plays, or that the session is portable. The session may change during inspection. `lanes` lists every direct audio lane in track and Program item timelines with its `part`, `itemIndex` for Program items, zero-based `audioIndex`, attributes and clip count. `clips` lists every direct audio clip with `audioIndex`, `clipIndex`, its attributes, and `mapping`: the `media.map` row whose source path exactly equals the clip `file`, with that sidecar's status. `mapping` is `null` when no row matches and `{ambiguousLines}` when several rows share the source path (also reported as `duplicate_source`). Use these indices for audio clip edits and removals. A match does not prove that ShowKontrol resolves the clip through that row. `unmappedMediaEntries` lists every entry below `MEDIA/` whose relative path no `media.map` row names exactly, with its kind (`regular_file`, `symlink` or `special_file`) and the size of regular files; symlinks are not followed. Whether ShowKontrol uses or needs such files is unknown.

- `showkontrol_preflight_session_audio`: check the media behind every direct audio clip in a session directory without writing anything. Supply an absolute session `directory`, and optionally `sha256` set to `showSha256` from `showkontrol_inspect_session_media` (the call fails if the session changed since inspection), `probeDurations` (default `true`) and `probeBudgetMs` (100 to 30000, default 10000). `clips` lists track and Program item clips in the order and with the `part`, `itemIndex`, `audioIndex` and `clipIndex` of `showkontrol_inspect_session_media`. Each clip has two candidates, and the tool does not choose between them. `sidecar` is the single `media.map` row whose source path exactly equals the clip `file`, checked below the session without following symlinks; it is `unmapped`, `ambiguous_mapping` with the row lines, or a sidecar status of the inspect tool. `sourcePath` is the `file` attribute as a path on the computer running the server, with symlinks followed as in `showkontrol_preflight_rpp_media`; it is `no_file_attribute`, `empty`, `not_absolute` (relative paths are not resolved), `invalid_path`, `not_found_at_checked_path`, `not_regular_file`, `check_failed` with `errorCode`, or a regular file, with `viaSymlink` when the path itself is a symlink. Each regular file is opened read-only, without following a sidecar symlink. It is `readable` only if the opened descriptor is still the regular file that was checked (same device and inode); otherwise it is `changed_during_check`, and an open failure is `not_readable` with `errorCode`. Paths that name one file (the same path in several clips, hard links, symlinks, or a clip file that is also the sidecar) form a single `files` entry with every `paths` entry, its `size` and `clipCount`. Each candidate's `fileIndex` selects that entry, and each file is opened and probed once. Directories, FIFOs and other special files found during the check are reported without being opened or probed; the open uses non-blocking mode in case one replaces a checked file.

  With `probeDurations`, `ffprobe` from the server's `PATH` reads the opened descriptor (`-fd 3 -i fd:`) with only the `fd` protocol allowed. It therefore reads exactly the checked file. A playlist or manifest, such as a DASH file that names a local segment, cannot make it open another file, and such files report an unknown duration. Each file's `duration.status` is `known`, `unknown`, `unavailable`, `not_checked` or `disabled`. `known` gives `seconds`, the container duration that ffprobe reports. `unknown` gives a `reason`: `no_container_duration`, `ffprobe_failed`, `fd_input_unsupported` (the installed ffprobe does not accept descriptor input; tested with ffprobe 7.1.5 on Linux), `invalid_output`, `output_too_large` or `timeout`. `unavailable` means ffprobe was not found; no later probes run in that call. `not_checked` means the file was not readable or the budget was used up (`reason: budget_exhausted`). `disabled` means `probeDurations` was `false`; files are still opened to check readability. When ffprobe output was parsed (`known`, or `unknown` with `no_container_duration`), the result includes `formatName`, `audioStreamCount`, `audioStreams` (stream `index` and `seconds`, `null` when ffprobe gives none) and `estimatedFromBitrate`, which is `true` when ffprobe warned that it estimated the duration from the bitrate. Parsed results and failed probes include up to five `warnings` lines from ffprobe. A truncated WAV whose header declares more data than the file holds produced such a warning in a test. Up to four probes run at once and share the time budget; each is stopped at the deadline. Container and stream durations can differ, and neither is shown to equal the length that ShowKontrol uses.

  Each clip's `observedTrim` gives `trimStartMs` and `trimEndMs` exactly as stored: `null` when absent, and `{length, valueOmitted}` for values over 256 characters. No clip is compared with a duration, and `trimComparison.status` is always `not_established`; see [Clip trims and media duration](evidence.md#clip-trims-and-media-duration). The tool supports up to 1,000 distinct media paths, uses the inventory limits of `showkontrol_inspect_show_media`, and rejects results over 4 MiB. `diagnostics` repeats the inventory diagnostics, such as `duplicate_source`. Which candidate ShowKontrol uses, whether it searches other locations, format and codec support, waveform caches, relinking and playback are not verified. A readable file with a known duration is not evidence that a clip plays correctly.

- `showkontrol_compose_session_media_copy`: create a new session directory from an inspected session directory. Supply `source`, a new `destination` directory whose parent exists, and `sha256` set to `showSha256` from `showkontrol_inspect_session_media`. Each `media` entry names an absolute media file on the computer running the server, plus an optional `sidecarName`; the default is the source file name. The tool appends one `<source path>\t<MEDIA/name>` row per entry to `media.map`, creating the part if absent and keeping an existing byte-order mark and line-break style. It copies every mapped sidecar from the source session, and each new file, into the new `MEDIA/` folder. Each copy is read from a file descriptor that must match the planned file, then re-read and compared by SHA-256. Optional `tracks`, `patchOperations`, `setlistOperations`, and `program` follow `showkontrol_compose_full_show_copy`, so one call can compose media, patch, tracks, set lists, and a Program schedule or ordered Program edits into a new session. Staged Program donors select tracks of the same call by `trackIndex`, as in the full-show composer. An audio clip can use `mediaIndex` instead of `clip.file`; the selected source path becomes `file`. A Program item timeline embedded from a staged track carries those clips. The inventory then matches each clip to its row; whether ShowKontrol resolves a track or Program item clip through that row is unverified. The result reports added rows, copied sidecars with sizes and SHA-256 values, clip-to-mapping links, and how each working file was carried over.

  Existing clips and lanes are changed with the track fields of the composers: `audioClipEdits` (including `file` to change the clip media), `audioClipRemovals`, and `audioLaneRemovals`. In a session, an audio clip edit can use `mediaIndex` instead of `attributes.file`; the selected new media source path becomes `file`. Ordered Program edits in `program.operations` change clips in existing Program item timelines in the same way: `add_timeline_audio_clip` can use `mediaIndex` instead of `clip.file`, and `edit_timeline_audio_clip` can use it instead of `attributes.file`. Other Program operations reject `mediaIndex`, and the non-session composers do not accept it. Program item clips added or re-pointed this way appear in `programClipLinks` at their final positions, with the `program_clip_file_unmapped` and `program_clip_sidecar_missing` warnings, and `program.audioOperations` holds the operation receipts. An existing mapped source path can be given as `attributes.file`. Each edit that sets `file` gets a `clipLinks` entry with `clipEditIndex` in place of `clipItemIndex`, and `clip_file_unmapped` or `clip_sidecar_missing` warnings as for new clips. Removing or re-pointing clips keeps every `media.map` row and copies every mapped sidecar; rows change only through `mediaMapOperations`, described below. A kept row whose source path was named by a track or Program clip before the composition and by none after it produces a `mapping_no_longer_referenced` warning with its line in the new `media.map`, source path and archive path. Whether ShowKontrol needs, ignores or removes such rows is unverified. The changed timeline's exact `TIMELINE/` extraction is rewritten from the composed part by the working-file rules below. A failed audio operation publishes nothing.

  `mediaMapOperations` removes or re-points existing rows of the source `media.map`, with the operations of `showkontrol_edit_media_mappings_copy`: `remove_mapping` and `repoint_mapping` select one row by its inspected `line` and exact `sourcePath` and `archivePath`, and `repoint_mapping` sets `newSourcePath`, `newArchivePath` or both. Lines are those of the inspected source session; the rows are edited in the composed archive, and new `media` rows are appended after them. New media is checked against the edited map, so a removed row's source path or released sidecar name can be used by a new media entry. A value that leaves the map (the source or `MEDIA/` path of a removed row, or the old value of a re-pointed column, unless a remaining or new row keeps it) must not be named anywhere in the composed `session.skshow`, searched as for the show tool, or in a working file carried into the new session. Working files outside `MEDIA/` are searched as text, and for UTF-16 forms; a file that is not UTF-8 is searched for the literal UTF-8 and UTF-16 byte forms without boundaries. Regenerated extractions are searched in their new form, omitted files are not searched, and files below `MEDIA/` and extractions of `media.map` are not searched. While a value leaves the map, a working file outside `MEDIA/` larger than 128 MiB fails the call, because it is not searched. Re-pointing `archivePath` copies the sidecar, byte-verified, under the new name; `sidecars` reports it with `renamedFrom`. The new name must not collide with any session entry. A sidecar left without a row fails the call unless `removedSidecars` is `keep`, which copies it as an unmapped working file, or `omit`, which leaves it out of the new session. A released sidecar must be a regular file or missing. The source session is never changed. `mediaMap.operations` gives each operation's row before and after, with its new line, and `oldSidecar` (`still_mapped`, `kept`, `omitted` or `missing`). `mediaMap.unmappedSidecars` lists the `MEDIA/` files of the new session that no row names, including released sidecars that were omitted, with `reason` `mapping_released` (and the released lines) or `unmapped_in_source`. If every row is removed, the part is kept with no rows and a `media_map_empty` warning is reported. A call with only mapping operations is not validated, like a media-only call. Whether ShowKontrol needs a removed row, accepts an edited map, relinks a re-pointed row or uses a sidecar under its new name is unverified.

  When any composition input is supplied, the composed archive must pass `showkontrol_validate_show` without errors before anything is staged; after new `media.map` rows are appended, the final `session.skshow` is validated again. The result's `validation` describes that final archive and names the published `session.skshow`. Validation has the partial coverage described for `showkontrol_validate_show`. A media-only call is not validated, as before; call `showkontrol_validate_show` on `sessionFile` if needed. When `program` is supplied, `programClipLinks` lists every direct audio clip in the final Program's item timelines with its `itemIndex`, `audioIndex`, `clipIndex`, `file`, and matching `media.map` line; a nonempty unmapped file produces `program_clip_file_unmapped`, and a mapped file whose sidecar was allowed to be missing produces `program_clip_sidecar_missing`. The result also includes the full-show `program` receipt with item ID mappings. A new Program part follows the working-file rules for new parts below: it gets an extraction only if the source session shows a consistent `.skpr` layout, and the call fails if `.skpr` working files exist without one. The generated Program, its item ordering and graphs, and Program clip media have not been opened or played in ShowKontrol.

  A new track created from an empty template can receive `audioLanes` and `audioClips`. The R27 27.0.11 app-saved empty track has no deck and already holds one lane, `Audio 1`, at `audioIndex` 0; clips can target it with `audioIndex: 0`, and added lanes are appended after it, so the first added lane gets `audioIndex` 1 and adding another lane named `Audio 1` fails. A template lane can also be removed with `audioLaneRemovals`; added lanes then move down, as the receipt reports. The deckless layout rules of `showkontrol_add_timeline_audio_lane_copy` apply; a template that does not match them fails the composition and publishes nothing. Whether ShowKontrol accepts and plays such a track has not been tested.

  The tool rejects relative or non-normalized source paths, paths through a symlinked directory (the error names the resolved path to supply instead; on macOS this includes `/tmp` and `/var`), symlinks, special or empty files, sources already mapped, tabs or line breaks in paths, and sidecar names that collide with a mapped sidecar or an existing session entry without case or after Unicode normalization. It also rejects a malformed or duplicate `media.map`, the creation of `media.map` beside a part with a similar name (as for `showkontrol_add_media_mappings_copy`), unsafe or symlinked mapped sidecars, files that change during copy, and copies above `SHOWKONTROL_SESSION_MEDIA_MAX_BYTES` (default 4 GiB) or the destination's free space. A missing mapped sidecar fails unless `allowMissingSidecars` is `true`; its row is then kept and reported. The session is assembled in a sibling staging directory, checked with the read-only inventory tools, and published after the source `session.skshow` hash and working tree are checked again. An existing destination is rejected before any work starts.

  Publication never deliberately replaces anything at the destination. Node.js `fs.rename` is `rename(2)`, which replaces an empty destination directory, and Node.js has no rename flags. The tool therefore uses one of two methods, chosen per call and reported in the result's `publication` (`method`, `atomicNoReplace`, `fallbackReason`, `note`):

  - `renameat2_noreplace` (Linux, `renameat2` with `RENAME_NOREPLACE`, glibc 2.28 or later) or `renamex_np_excl` (macOS, `renamex_np` with `RENAME_EXCL`, macOS 10.12 or later). The kernel renames the staged session to the destination in one step and fails with `EEXIST` if anything exists there, including an empty directory; the call then fails with `Destination session already exists; the no-replace rename left it unchanged`. These functions are reached through the built-in `node:ffi` module, which is experimental. Node.js 26.1.0 through 26.8.1 provide it only in builds with FFI support and only when Node.js is started with `--experimental-ffi`; the documentation of both releases says the module "is gated by the `--experimental-ffi` flag". A Node.js version alone does not enable it, and the server never adds the option itself; see [Atomic session publication](setup.md#atomic-session-publication). The module is not used when it is missing (Node.js before 26.1.0, or a build without FFI support; such a runtime does not accept `--experimental-ffi`), not enabled (started without `--experimental-ffi`, or with `--no-experimental-ffi`), denied by the permission model (`--permission` without `--allow-ffi`), or cannot bind the function. `fallbackReason` names the case from the runtime's own option list (`process.allowedNodeEnvironmentFlags`), `process.execArgv` and `NODE_OPTIONS`, not from its version. The permission model does not check FFI calls against `--allow-fs-write`, so under `--permission` the native rename is used only when `process.permission.has('fs.write', …)` grants both the staging directory and the destination; otherwise the fallback, whose `fs` calls the permission model does check, is used. Before anything is copied, each call probes the primitive inside its staging directory, on the destination volume: renaming onto an existing empty directory must fail with `EEXIST` and leave both directories, and renaming to an absent name in another directory must move the directory. A volume that does not support the flag (for example a macOS volume without `VOL_CAP_INT_RENAME_EXCL`, or a Linux file system that returns `EINVAL`) or that ignores it fails the probe. Only the return value decides whether anything moved. `errno` is read in a second native call after the rename returns; if something in between overwrote it, the probe fails and the fallback is used, or a failure message names the wrong error. A failure other than `EEXIST` says `nothing was published` only when the staged session is still in staging (same device and inode); otherwise the message asks to check the destination. The bindings follow the C declarations `int renameat2(int, const char *, int, const char *, unsigned int)` with `AT_FDCWD` (-100) and `RENAME_NOREPLACE` (1), and `int renamex_np(const char *, const char *, unsigned int)` with `RENAME_EXCL` (4); paths are passed as NUL-terminated UTF-8 buffers, and a path containing NUL is refused. A wrong signature or constant can crash the server instead of failing a call, which the probe cannot detect.
  - `claim_rename`, the fallback, whenever the primitive is unavailable or fails its probe; `fallbackReason` says why. The destination is created with `mkdir` just before the rename, which fails if anything exists there, checked to be still that directory (same device and inode), and the staged session is renamed over the empty claim. The check and the rename are separate steps, so this does not exclude concurrent processes. A process that swaps the claim for its own empty directory between the check and the rename has that directory replaced, and the call reports success without a warning; writes through a handle to the replaced directory do not reach the published session (on Linux they fail with `ENOENT`). An entry another process writes into the claim before the rename makes the call fail with `Destination session changed during publication`; the claim and that entry are left in place.

  `requireAtomicPublication: true` makes the call fail with `Atomic no-replace publication is unavailable: <reason>` instead of using the fallback. The check happens before any media is copied. Node.js 22 and 24 have no `node:ffi`, so only the fallback is available; Node.js 22.23.2, this repository's Linux test environment, refuses `--experimental-ffi` at startup (`bad option`, exit code 9), which the tests check. On the owner's Mac with Node.js 26.8.1 (owner-reported, 15 November 2026), `SHOWKONTROL_EXPECT_ATOMIC_PUBLICATION=1 node --test session-publication.test.js` failed because `node:ffi` was not enabled, and the same test with `--experimental-ffi` passed and reported `renamex_np_excl` in the test's temporary directory on that Mac. That is the only execution of the binding. The Linux `renameat2` binding through `node:ffi` has not been executed; its no-replace semantics were exercised through the same `renameat2` call made from Python `ctypes` on ext4 and tmpfs. After publication the session is an ordinary directory; later writes into it are not detected.

  A failed call publishes nothing of its own, and the source session is not modified.

  Each call stages in one directory beside the destination, `.showkontrol-session-staging-<32 hex>` (mode `0700`), holding `owner.json`, `work/` (intermediate archives), `session/` (the session that is renamed to the destination) and, in the fallback only, `claim.json`. `owner.json` records the tool, the token in the directory name, the directory inode, the destination name, the creation time, the host name, the platform, the process ID, a random token of the server process and, on Linux, the boot identifier and PID namespace. A running call touches `owner.json` every 15 seconds, without following a symlink. `claim.json` is written before the destination is claimed (`claiming`) and again with the claimed directory inode (`claimed`). The staging directory is removed when the call returns or fails, with `owner.json` last; if that removal fails, the result reports it in `cleanupWarnings`, or the call fails when nothing was published.

  If the server process is killed or the computer loses power, the staging directory remains and can hold full media copies. In the fallback, a kill between the claim and the rename also leaves an empty destination directory. A retry to that destination then fails as already existing, and the message names the staging directory when the claim has been verified. A new call never removes staging directories. It reports verified stale ones in the same parent with a `stale_session_staging` warning (`names`, `bytes`). Use `showkontrol_find_session_staging` and `showkontrol_remove_stale_session_staging`, described below. Copied sidecars and copied working files are synced to disk. The composed `session.skshow`, rewritten working files, directories and the rename are not, so a power loss shortly after a call returns can leave the published session missing or incomplete.

  Other session entries are working state and are carried over. The only app evidence is that opening a generated `.skshow` wrote a working `session.skf` equal to `patch.skf` except for the root `name`; there is no app evidence for `settings.json` or `TIMELINE/`. Each working file is related to an archive part: `session.skf` to `patch.skf`, a file whose path is a part name to that part, otherwise a part with identical bytes, otherwise a part with the same file name. The result's `workingFiles` reports each file's `action` and `relation`:

  - `exact` or `root_name` (`session.skf` equal to `patch.skf` except the root name): copied if the part is unchanged, `regenerated` from the composed part if it changed (keeping the working root name), and omitted if the part was removed.
  - `diverged` or `name` (it differs from its part, for example unsaved working edits): copied with a `working_file_differs_from_archive` warning if the part is unchanged. If the part changed, neither copying nor regenerating is safe, and the call fails.
  - `none` (for example `settings.json`): copied, unless its extension, or `.sktl` for files under `TIMELINE/`, matches a part the composition changed; then the call fails.
  - For a new part, a file is `created` when every exact extraction of that part type in the source uses `<directory>/<part file name>` in one directory. If no consistent layout exists but working files of that type do, the call fails.

  Symlinks and special files in the session also fail. Set `omitUnverifiedWorkingFiles` to `true` to leave such entries out instead; each one is reported with a `working_file_omitted` or `working_file_not_created` warning. Whether ShowKontrol then regenerates them, and whether it reads working files or `session.skshow` when it opens a session directory, are unverified. Permissions and timestamps are not preserved. The layout follows one R27 session after a REAPER import; see [REAPER and marker files](#reaper-and-marker-files). ShowKontrol has not opened, relinked, or played a generated session. Synthetic tests do not establish media format, duration, waveform caches, or clip timing against the media.

### Session staging

- `showkontrol_find_session_staging`: list session staging directories in an absolute `directory`, the parent of session destinations, without changing anything. Entries are `.showkontrol-session-staging-*` directories (`kind: staging`; a name ending in `.removing-<16 hex>` was left by an interrupted removal, is marked `interruptedRemoval: true` and is verified the same way) and the `.showkontrol-session-*` and `.showkontrol-session-work-*` names of earlier versions (`kind: legacy`). Each entry has `status` and `reason`. `stale` requires every one of these: the entry is a real directory (not a symlink) owned by the current user, its `owner.json` is a regular file of this tool whose token equals the directory name and whose inode equals the directory's, the record was written on this host name and platform (and on Linux in the same PID namespace with a known boot identifier), the owner process is gone (no process has its ID, or on Linux the boot identifier changed), and `owner.json` has not been touched for `staleAfterMs` (120000). `active` means a call in this server process is using it, a process with the recorded ID is running (it may be a reused ID, so such an entry is kept until that process exits), or the record was touched recently. Everything else, including legacy names, copies under another name, recreated directories, symlinks, records from another host name and directories without a record, is `unverified` and never removed by the tools. Stale entries report `bytes` (bounded at 10000 entries, `truncated`). A fallback claim recorded in `claim.json` is reported as `claim` with `status` `empty_claim` (still the recorded inode and empty), `not_empty`, `replaced`, `absent` or `unverified` (the inode was not recorded). Owner checks are per host: two computers with the same host name sharing a volume are not distinguished, which the 120-second idle requirement guards against only while the other computer's call is running and touching its record.

- `showkontrol_remove_stale_session_staging`: remove named staging directories that the find tool reports as `stale`. Supply the same absolute `directory` and 1 to 100 `names`; anything other than a `.showkontrol-session-staging-<32 hex>` name, optionally followed by `.removing-<16 hex>`, fails the call before anything is removed. Each entry is verified again immediately before removal. Entries that are not stale are listed in `kept` with their status and reason. A stale entry is first renamed to `<name>.removing-<16 hex>`, and the moved entry must be the verified directory: not a symlink (`rename(2)` moves a symlink itself, not its target), same device and inode. Otherwise nothing is removed, the entry is renamed back when its name is still free, and it is listed in `kept` with status `changed`. Then an `empty_claim` destination is removed with `rmdir`, which fails on a directory with entries, after checking that it is still the recorded inode on the same device; otherwise the claim is kept with status `changed`. Other claims are kept and reported. Then the staging contents are removed without following symlinks, with `owner.json` last. `removed` reports each name, `removedAs`, `bytes` and the claim action. An interrupted removal leaves the `.removing-` name; its record still matches its token and inode, so it can be found and removed again. Limits: Node.js removes by path, not through a directory handle, so a process of the same user that replaces the `.removing-` directory or a subdirectory inside it during removal is not excluded. A different empty directory put at the destination between the claim's inode check and `rmdir` is removed; a directory with entries cannot be. Some file systems, for example ext4, reuse inode numbers after deletion, so a directory deleted and recreated with the same inode is not told apart.

## REAPER and marker files

- `showkontrol_create_marker_csv`: create a REAPER marker/region CSV for manual import into the Cue Editor. It writes a new file only. Times are rounded to milliseconds. Marker and region import has not been verified in ShowKontrol; the file does not contain action graphs.

- `showkontrol_create_rpp`: create a new `.rpp` file with markers, empty cue items, and audio or video media items. It does not overwrite an existing file. Import it with Cue Editor > REAPER > Import. Choose the target layers and check the import preview before you commit it. The item and media generators have not been verified in ShowKontrol.

- `showkontrol_preflight_rpp_media`: check the media paths for an intended RPP project without creating or changing files. Pass an absolute `.rpp` path as `file` and the same `mediaTracks` input used by `showkontrol_create_rpp`.

Neither the RPP nor the marker CSV contains cue action graphs. It does not create a ShowKontrol track, import itself, or save a show. It cannot provide full show authoring.

### Media project input

Use `mediaTracks` in the `showkontrol_create_rpp` arguments. Each track has a `name`, a `kind` of `audio` or `video`, and an `items` array. Each item has a `file` path, `seconds`, and `duration`. Optional item fields are `name`, `sourceOffset`, `fadeIn`, `fadeOut`, and `takeVolume`. Times are seconds. Take volume is a linear multiplier: `1` is unity and `0.5` is approximately −6 dB. Fades are linear. The optional track `nativeColor` is a REAPER native colour integer, including its custom-colour flag. Native colour byte order depends on the computer that created the project.

Audio files must use `.wav`, `.mp3`, or `.flac`. Video items use REAPER's `VIDEO` source type. The generator does not check media existence, media duration, codecs, or whether the destination Mac can read a path. Use paths that exist on that Mac, or paths relative to the RPP file. Place the media where ShowKontrol can find it. The import dialog can still list missing media. The file only references media; it does not copy or embed it.

The media preflight checks each absolute path as given, or resolves a relative path against the intended RPP directory. It reports the checked path and whether it is a readable regular file, is not a regular file, was not found at that path, or could not be checked. It follows symlinks and reports duplicate references separately. It accepts up to 100 tracks and 500 items, with paths and names limited to 4096 characters. It checks access on the computer that runs the server at the time of the call. A missing result applies only to the checked path: ShowKontrol may search other locations. Set `probeDurations` to `true` to check readable regular files with `ffprobe`, if it is installed on the server. Each finding reports whether duration is known, unknown, unavailable, not checked, or disabled. When known, `seconds` is the reported container duration and `exceedsSource` indicates whether `sourceOffset + duration` exceeds it. Unknown or unavailable duration does not establish whether the item fits. Probes share a five-second time budget per request and permit only local file protocols. Repeated checked paths reuse the probe result. Files left after the time budget are reported as not checked. Container duration can differ from a stream duration. The check does not verify media format, codec, or import into ShowKontrol.

The generated files have passed structural tests and an independent RPP parser. In one R27 27.0.11 test, a generated project imported two WAV items and two cue items into a disposable track. The app displayed both audio clips and cues. After save, the timeline recorded the requested positions, source trims, and fades. The imported clips had no `vol` attribute, so the requested take volumes are not verified. The session contained byte-identical copies of both WAV files in its `MEDIA` folder. Its `media.map` mapped the original absolute source paths to those sidecar files; the `.skshow` did not contain matching `MEDIA/` parts. Playback, reopening without the original sources, portability, other formats, and REAPER playback remain unverified. Check the import preview, target lane, offsets, fades, and level before use. ShowKontrol's manual describes audio-lane import with source offset, length, fades, and take volume. It describes video-lane import, but does not promise that all audio-item properties also apply to video.
